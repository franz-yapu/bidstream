# bidstream

Motor de subastas orientado a eventos (Node/TS, Kafka, PostgreSQL+Prisma, GraphQL, Azure/Bicep).
Spec normativa: `docs/product/bidstream_spec.md`. PRD/alcance/reglas en `docs/product/`.

## Método (SDD)

1. Planificación: skills `prd-to-tickets` → backlog, roadmap, tickets en `docs/planning/`.
2. Por ticket: `write-sdd` genera `docs/sdd/<ID>/SDD.md` ANTES de codear; luego `task-brief`.
3. Código solo después de un SDD aprobado. Decisiones → ADR (`docs/adr/`) o `docs/decisions/LOG.md`.
4. Respetar `docs/do-not-touch.md`.

## Convenciones

- TypeScript estricto, dominio sin dependencias de infraestructura (hexagonal).
- Dinero en `Decimal(12,2)`. Conventional commits. Documentación en español.
- Pruebas de integración con Postgres y Kafka reales en contenedores.

## Comandos

- `npm ci` instala; `npm run check` = build + typecheck + lint + format:check + test (quality gate). El build va primero: los paquetes se resuelven entre sí desde `dist/`.
- ESM con NodeNext: los imports relativos llevan extensión `.js` (`import { x } from './x.js'`).
- `packages/domain` no puede importar infraestructura (regla de ESLint, ver `docs/do-not-touch.md`).
- `make up` levanta Kafka (apache/kafka 4.3.2, KRaft) y PostgreSQL 16 y crea los topics; `make verify` los comprueba; `make reset` borra datos.
- Desde el host: `KAFKA_BROKERS=localhost:9092`; desde contenedores: `kafka:19092`.
- La CI (`.github/workflows/ci.yml`) ejecuta `npm run check` en Node 22; las acciones se fijan por SHA de commit. `main` se cambia solo por PR.
- Usar **Node 22** (`nvm use`): `@confluentinc/kafka-javascript` no compila en Node 26. `npm run test:integration` (requiere `make up`) corre los `*.int.test.ts`.
- `make migrate` aplica las migraciones de `packages/db`; el cliente Prisma se genera en `postinstall` (`npm run db:generate -w @bidstream/db`). Cambios de esquema: `npm run db:migrate:dev -w @bidstream/db` con `DATABASE_URL` y revisar el SQL; los índices parciales van a mano.
- `npm run dev:api` arranca la API (`apps/api`, Fastify + Zod, `buildApp(deps)` es el punto de composición). Errores siempre `problem+json`, sin trazas al cliente. Los DTO reutilizan `primitives` de `@bidstream/domain`.
- Pruebas de integración: usar `@bidstream/testing` (`createTestDatabase`, `createTestTopic`, `collectMessages`, `waitFor`); cada suite tiene su base de datos y sus topics desechables y **nunca** escribe en los topics reales. Solo se importa desde `*.test.ts` (regla de ESLint). La CI tiene un job `integration` aparte (no requerido por ahora).
- Acceso a datos: `withTransaction(prisma, async ({ lots, auctions, outbox }) => …)` de `@bidstream/db`; los repositorios son de solo lectura y filtran por tenant, y los eventos se escriben con `outbox.enqueue(events, topic)` en la misma transacción.
- Consumidores: `createEventConsumer` de `@bidstream/consumer`; cada uno aporta solo su `handler(event, { tx })`. El evento se registra en `processed_event` en la misma transacción; 4 intentos y luego DLQ (`dlqMessageSchema`). En pruebas, esperar a `onOutcome` (se emite tras el commit), no al retorno del handler.
- Comandos HTTP: la ruta solo traduce; la lógica está en `apps/api/src/commands/` (`openAuction`, `publishLot`) y escribe el evento en el outbox con `withTransaction`. El `201` es «aceptado». La API necesita `DATABASE_URL`; con `NODE_ENV=production` no arranca hasta F1 (tenant por cabecera prohibido). Los ids de aggregates los genera el servidor (UUID v7).
- Relay (`apps/relay`): un solo líder activo (bloqueo asesor sobre una conexión `pg` dedicada); `runOnce()` devuelve solo lo confirmado. El orden de publicación es `(created_at, id)`: C3 debe serializar los comandos de un mismo lote al escribir. `claimPending` solo se usa dentro de una transacción.
- Proyección: `applyEventToProjection(tx, event)` (`@bidstream/db`) traduce cada evento a escrituras y **lanza** `ProjectionError` si el estado es incoherente. `lot.auction_id` no tiene clave foránea (ver D4 §2.4). Reprocesar = `resetProjection` (borra también `processed_event` del `projector`) + reposicionar el grupo a `earliest`; nunca como ruta HTTP. Flujo local completo: `make up && make migrate` y `npm run dev:api` / `dev:relay` / `dev:projector`.
- Bitácora: `audit_log` es **append-only** (disparadores en la migración 0003; en producción además un rol con solo INSERT/SELECT, H1). Solo se escribe con `recordAuditEntry`; nunca se actualiza ni se borra, y `resetProjection` no la toca. `npm run dev:auditor` la alimenta.
- Reproceso: `npm run reprocess -w @bidstream/projector -- --yes` (nunca como ruta HTTP). Reposicionar = borrar el grupo vacío (`createKafkaAdmin().deleteGroup`): el cliente no tiene `setOffsets`. Las pruebas de consumidores usan un **grupo único por ejecución** (`createProjector({ groupId })`) porque `projector` es global en el clúster. `apps/*` importa los paquetes desde `dist/`: recompilar tras tocar un paquete. Procesos de demostración: arrancar con `node --import tsx` (no `tsx`) para poder terminarlos por PID sin dejar un hijo vivo.
- Notificaciones: `@bidstream/notifier`. Un único grupo `notifier` hace `pg_notify` **dentro de la transacción** del consumidor base; cada réplica GraphQL escucha con `startNotificationListener` (conexión `pg` dedicada) y reparte con `InMemoryNotificationBus`. Las notificaciones se derivan solo del evento y **nunca llevan `bidderId` ni `winnerId`**. Entrega best-effort: `onResync` indica recargar. En pruebas, usar un grupo único (`createNotifier({ groupId })`).
- GraphQL (`apps/graphql`): solo lecturas, `buildYoga({ config, db })` sin escuchar (las pruebas usan `yoga.fetch`). Dinero como `Money` (cadena) y fechas ISO UTC; **ningún campo expone `bidderId`/`winnerId`**. Cursor opaco _keyset_ sobre `(amount DESC, placedAt, id)`. Bajo Vitest `graphql` debe cargarse como una sola copia (`server.deps.inline` en la config de integración). `Lot.auction` es nulo-able (consistencia eventual). Arrancar procesos con `node --import tsx` para poder detenerlos por PID.
- Límites GraphQL (`apps/graphql/src/limits`): profundidad (cuenta también la hoja), alias, complejidad con coste `first × (1 + hijos)`, tokens, cuerpo, batching off e introspección configurable; se aplican antes de los resolvers. Errores de validación: 400 solo con `Accept: application/graphql-response+json`. Todo configurable con `GQL_*`.
- Subscriptions: `lotUpdated` por SSE (Yoga). El servidor recibe un `NotificationBus` (D5); `main.ts` arranca `startNotificationListener`. Cola acotada por suscriptor (`ResyncRequired` al desbordar) y cupo por tenant. Los errores previos al flujo llegan como JSON solo si el cliente acepta `application/graphql-response+json`. En pruebas, cancelar el flujo (`reader.cancel()`), no solo el `AbortSignal` de `yoga.fetch`; y el cliente SSE debe leer en segundo plano (Yoga solo suscribe al empezar a leer). La prueba `flow.int.test.ts` recorre los seis procesos.
- DLQ (D7): `peekDlq`/`reprocessDlq` en `@bidstream/consumer` (grupo `dlq-reprocessor`, un solo reproceso a la vez → 409; tope `MAX_REPROCESS=3` vía `reprocessCount`/cabecera `x-reprocess-count`). La API expone `GET /v1/admin/dlq` y `POST /v1/admin/dlq/reprocess` **solo al rol `ADMIN`** (token; antes `X-Admin-Key`, retirada en F1) y solo si hay autenticación configurada. Kafka se importa de forma diferida (`lazyDlqAdmin`). El log registra `requestId` y `eventIds`, nunca el contenido. El evento reprocesado va al final de su partición.
- Logs (F4): `@bidstream/logging` (`createLogger({ service, level })`, una línea JSON por evento, redacta claves sensibles y contraseñas de URL; `LOG_LEVEL`). Todos los procesos lo usan salvo la API (pino con los mismos campos). El `request.id` de la API viaja como `meta.correlationId` del evento → cabecera Kafka `correlationId` (la copia el relay) → logs del consumidor (`evento procesado`, duplicado, reintento, DLQ) y `DlqMessage.correlationId`. Nunca se registra el `payload` de un evento ni `bidderId`. Prueba: `apps/projector/src/correlation.int.test.ts`.
- Imágenes (H2): un `Dockerfile` con `ARG APP` (`api|relay|projector|auditor|notifier|graphql|decider|closer`), multi-etapa, `node:22-bookworm-slim` por digest (no Alpine: binario nativo de Kafka), usuario `node`, sin fuentes ni `.env`; `make images` las construye. `scripts/docker-smoke.sh` las arranca de verdad (solo en CI o con `SMOKE_DISPOSABLE=1`: los procesos usan los grupos reales y consumirían de un clúster con datos). La API con `NODE_ENV=production` no arranca hasta F1: el humo la lanza con `NODE_ENV=development`. Política en `packages/testing/src/policy/docker-policy.test.ts`.
- Demostración del reproceso (H5): `make demo-reprocess` (`scripts/demo-reprocess.sh`, requiere `make up`) usa su propia base, topic (`bidstream.demo.events.<n>`) y grupo (`projector-demo-<n>`), compara una huella SHA-256 de la proyección antes y después (`apps/projector/src/demo/`) y termina `IDÉNTICO ✔` o falla. `PROJECTOR_GROUP_ID` y `PROJECTOR_TOPIC` (por defecto los reales) las usa también el CLI `reprocess`; `KAFKA_LOG_LEVEL=error` silencia el ruido del cliente. Guion del vídeo: `docs/demo/GUION.md`.
- Documentos: `README.md` es el de producto (spec §12; lo vigilan las pruebas de `packages/testing/src/docs/readme.test.ts`: secciones, enlaces, comandos y honestidad) y `docs/DESARROLLO.md` la guía técnica del día a día. `make demo` levanta todo en contenedores (perfil `app` de `docker-compose.yml`, `NODE_ENV=development`) y `scripts/demo-smoke.sh` lo comprueba (job `demo` de la CI); `make down` también detiene el perfil `app`. Al grabar el vídeo, sustituir `<!-- VIDEO-PENDIENTE -->` y la línea «Vídeo: pendiente» del README por un enlace `**Vídeo:** [..](https://…)`.
- Puja (C3): `POST /v1/lots/:id/bids` solo **acepta** (`202`, cuerpo `{ amount }`; cabeceras provisionales `X-Tenant-Id` y `X-Bidder-Id`, solo fuera de producción) y escribe el comando `PlaceBid` (`@bidstream/domain`, `buildCommand`/`parseCommand`) en el outbox con `enqueueCommand`. `apps/decider` (ADR-0011) tiene dos consumidores: `decider` sobre `bidstream.commands.bid` (usa `decidePlaceBid`: bloquea `lot_decision` con `FOR UPDATE`, aplica `decideBid`, guarda el estado y encola los eventos en una transacción) y `decider-state` sobre `bidstream.events.lot` (`applyEventToDecision`). El nombre del consumidor `state` debe coincidir con su grupo (`DecideDeps.stateConsumer`). Un lote desconocido lanza `LotStateNotReady` (reintento → DLQ → reproceso D7, que también entiende comandos). `ANTI_SNIPING_WINDOW_MS`/`ANTI_SNIPING_EXTENSION_MS` (2 min por defecto). Reconstruir `lot_decision`: borrarlo y releer el log con un grupo nuevo (nunca con el mismo grupo, que ya tiene sus eventos marcados). `createMessageProcessor` es genérico (`codec`: `eventCodec`/`commandCodec`).
- Idempotencia de la puja (C4): `Idempotency-Key` obligatoria (16–128 caracteres `[A-Za-z0-9._-]`; `400` si falta). `placeBid` reclama la clave en la misma transacción que el comando (`PrismaIdempotencyStore.claim`, tabla `idempotency_key`, ámbito `(tenant, postor, clave)`): misma petición → mismo `commandId` y cabecera `Idempotency-Replayed: true`; otra petición → `422` (`idempotency-key-reused`). Un lote desconocido (`404`) no consume la clave. `countSince` (F2) y `deleteOlderThan` (limpieza que hará el `closer`, D8) ya existen.
- Cierre (D8): `apps/closer` (líder único por bloqueo asesor `7266451002`, `tryAcquireLeadership` vive en `@bidstream/db`) busca en la **proyección** lotes abiertos con `closes_at <= ahora` y encola el comando `CloseLot` (`commandId` determinista `deterministicUuidV7(close-lot:lotId:closesAt)`, `enqueueCommand(…, { skipDuplicates: true })`) por la partición del lote; el decisor lo resuelve con `decideCloseLot` y la hora del comando (si el anti-sniping extendió el cierre, no emite). Subastas vencidas sin lotes abiertos: `AuctionClosed` con id determinista. También borra cada hora las claves de idempotencia de más de 24 h. `CLOSER_POLL_MS` (5 s), `CLOSER_BATCH_SIZE`, `IDEMPOTENCY_RETENTION_MS`. El decisor es el único escritor de `LotClosed`.
- Firma (F3, ADR-0012): `@bidstream/signing` (Ed25519 con `node:crypto`). El relay firma los bytes exactos del valor (`signer` ← `loadSigningKey(env)`: `EVENT_SIGNING_PRIVATE_KEY` en base64/PEM + `EVENT_SIGNING_KEY_ID`) y añade `x-signature` y `x-key-id`; cada consumidor pasa `verifierFromEnv(process.env, timestampOf)` a su `verify` (`EVENT_SIGNATURE_MODE` = `enforce` en producción y `off` fuera, `EVENT_VERIFICATION_KEYS` = JSON `{kid: PEM}`, `EVENT_SIGNING_REQUIRED_FROM` = corte para el historial sin firma). Fallo → `poison` al DLQ. El DLQ guarda `signature`/`keyId` para que D7 republique con las cabeceras. `scripts/generate-keys.mjs` crea claves de desarrollo (`.env.signing.private` solo para el relay y `.env.signing.public` para el resto; no se versionan) y lo ejecuta `make demo`. Nunca loguear la clave privada.
- Autenticación y control de acceso (F1, ADR-0013): `@bidstream/auth` (`AuthService`: `createUser`, `login`, `refresh`, `logout`, `profile`; Argon2id; JWT de acceso EdDSA de 10 min con `sub`/`tid`/`role`; refresh opaco de 7 días, solo su SHA-256 en `refresh_token`, de un solo uso con rotación y revocación de la familia si se reutiliza; 5 fallos → bloqueo de 15 min; todo fallo de credenciales es el mismo `InvalidCredentials`). La API (`AUTH_MODE=jwt`, por defecto en producción; `header` —`X-Tenant-Id`/`X-Bidder-Id`— solo fuera de ella) expone `/v1/auth/{register,login,refresh,logout,me}` y `POST /v1/auth/users` (ADMIN crea ADMIN/SELLER/BIDDER **en su tenant**); límite por IP `AUTH_RATE_LIMIT_PER_MINUTE`. `registerAuthentication` deja `request.identity`; `JwtTenantResolver`/`JwtBidderResolver` leen tenant y postor **del token**. **Denegar por defecto** (`registerAccessControl`, solo en modo jwt): toda ruta exige token salvo las `config: { public: true }` (salud, docs, registro, login, refresh, logout) y debe declarar `config: { roles: [...] }` o se deniega con 403; `app.routeDeclarations` permite comprobar en pruebas que ninguna quedó sin política. Roles: crear subastas/lotes ADMIN+SELLER, pujar BIDDER, `/v1/admin/*` ADMIN (siempre, también en modo header). **Un gancho `onRequest` síncrono debe llamar a `done()`** (o ser `async`): si no, la petición se cuelga. GraphQL (`AUTH_MODE`) verifica el mismo JWT con `AUTH_JWT_PUBLIC_KEYS` y toma el tenant del token (`UNAUTHENTICATED` si falta o no vale). Claves: `AUTH_JWT_PRIVATE_KEY` + `AUTH_JWT_KEY_ID` (la pública se deduce) o `AUTH_JWT_PUBLIC_KEYS` (`{kid: PEM}`, rotación). Primer admin: `BOOTSTRAP_ADMIN_TENANT_ID/EMAIL/PASSWORD` (idempotente). `make demo` corre todo con `NODE_ENV=production`, JWT y firma obligatorios; `scripts/generate-keys.mjs` crea las cuatro familias de archivos `.env.{signing,auth}.{private,public}` (no se versionan) y una contraseña aleatoria para `admin@demo.local`.
- Endurecimiento (F2): límite de pujas por postor y minuto (`BID_RATE_LIMIT_PER_MINUTE`, 30): `placeBid` toma un bloqueo asesor de transacción por postor (`lockBidder`), reclama la clave y cuenta las claves de la última minuto (`countSince`, con la hora de la aplicación en `createdAt`); superado → `BidRateLimited` → `429` con `Retry-After` exacto y `RateLimit-*`, y la excepción revierte la clave reservada. Repetir una clave idempotente no cuenta. Compartido entre réplicas porque se cuenta en PostgreSQL. `@fastify/helmet` (CSP propia `default-src 'none'` salvo `/v1/docs`; HSTS solo en producción), `@fastify/cors` con lista blanca exacta `CORS_ALLOWED_ORIGINS` (vacía = sin CORS; `*` rechazado) y límite global por IP `API_RATE_LIMIT_PER_MINUTE` (por réplica; la salud no cuenta). Las defensas de borde se registran antes y los ganchos de identidad/acceso se añaden en `app.after(...)` para correr después (el preflight no lleva token). GraphQL: plugin `securityHeaders` y `cors` de Yoga con la misma lista. `pg_advisory_xact_lock` devuelve `void`: envolverlo en un `SELECT 1 FROM (...)`.
- ADR: `docs/adr/` (índice en su README; plantilla `0000-template.md`). Un ADR no se edita para cambiar de opinión: se escribe otro que lo reemplace. `packages/testing/src/docs/adr.test.ts` comprueba estructura, enlaces y evidencia.
- Dependencias: `package.json` raíz fuerza `minimatch ^11.0.8` (`overrides`); `npm run audit:prod` / `audit:high` = política de la CI. Toda acción de GitHub va fijada por SHA (lo comprueba `packages/testing/src/policy`). Dependabot no sube solo las mayores de `@types/node`, `graphql`, `prisma` y el cliente de Kafka.
